How much preview automation still feels simple?

This demo compares two label-gated lifecycles for at most three stable pull-request previews. Push them through capacity, stale runs, failures, and forgotten cleanup; then decide which operational burden is acceptable for one maintainer.

Question being tested: Is “label drives everything” worth its extra trusted event and reconciliation machinery, or is “label grants eligibility; the maintainer drives every action” safer and simpler despite the chores?

What each policy promises

Concern Automatic lifecycle Explicit manual lifecycle
Event surface Label/unlabel/close events plus every Product CI completion; both label-before-CI and CI-before-label must converge. One manual create/refresh action and one manual teardown action. PR events never mutate Dokploy.
Capacity A fourth eligible PR waits; successful teardown automatically admits the oldest waiter. A fourth create is refused; the maintainer tears one down and requests creation again.
Stale work Every run rechecks live label, PR head, CI result, and capacity. Stale work aborts; the newest green head is queued automatically. The same rechecks abort stale work, but the maintainer must request the new head.
Failure recovery No automatic retry or rollback. The maintainer reruns the failed revision. Same: rerun create/refresh or teardown explicitly; no rollback.
Cleanup owner Workflow tears down on unlabel/close, reconciles the waiting list, and audits swallowed runtime-cleanup failures. Maintainer tears down resources and retries failed cleanup; a periodic orphan audit catches forgotten work.
