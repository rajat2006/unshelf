# Book chapter discovery: feasibility and acquisition options

Research date: 2026-09-06. Source pages and prices are mutable; recheck before implementation.

Supports [Research reliable book chapter discovery with AI-assisted web search](https://github.com/rajat2006/unshelf/issues/603) in [Find book chapters with AI-assisted web research](https://github.com/rajat2006/unshelf/issues/602).

## Finding and recommendation

Public web evidence can support useful chapter suggestions, but this investigation does **not** establish a general success rate or an API quality benchmark. Recommend evaluating a bounded search-and-extract workflow: discover a source for the identified edition, read its actual contents list, extract ordered entries with evidence, and return an explicit inconclusive result when evidence is insufficient. Do not use model recall as a substitute for retrieval.

Start the provider evaluation with OpenAI Responses web search, compared against direct retrieval of a known source followed by extraction. Gemini grounding is technically plausible but its documented restrictions on modifying and storing grounded results present a concrete unresolved fit problem for editable, persisted Parts. This is an engineering recommendation, not a provider purchase decision or legal conclusion.

The confirmed product boundary is books only: **Find chapters** on the saved book; editable one-chapter-per-line preview; **Add chapters** creates ordinary, editable Parts. Title-only input, edition handling, partial-result acceptance, attribution presentation, and behavior when Parts already exist remain product decisions.

## Method and observed corpus

These are assisted retrieval observations, **not** calls to either candidate provider API, measurements of their latency, or a test of an implemented parser. No paid calls, accounts, or services were provisioned. The corpus deliberately includes technical nonfiction, numbered fiction, popular nonfiction, and two editions. It is too small and selected to estimate production coverage.

For either model path, a JSON schema constrains syntax, not whether a chapter exists. OpenAI documents a supported subset of JSON Schema and errors for unsupported strict schemas. Same-call compatibility of the final chosen model, search configuration, and output schema was **not tested** here. A separate extraction call is a fallback to evaluate, not a demonstrated necessity. Require application validation of the final object and evidence. [OpenAI structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

Do not select a specific model on this memo's evidence. Pin and test an available model during acceptance evaluation; per-attempt cost is search calls/queries plus discovery and extraction tokens, including retries. Dollar-per-book and p95 completion time remain unknown. A long-running deep-research agent is not justified by this small extraction task without a demonstrated coverage benefit.

## Provider constraints that affect the design

OpenAI's data guide says API data is not used for training by default; abuse-monitoring logs ordinarily retain content up to 30 days. Responses application-state retention has additional defaults and exceptions, so `store: false` is not a universal no-retention promise. Send bibliographic context needed for discovery, not unrelated User notes. [Data controls](https://developers.openai.com/api/docs/guides/your-data).

Google's terms require showing associated Search Suggestions with Grounded Results. They restrict copying/storage with specific exceptions and prohibit modifying or interspersing other content with Grounded Results absent written permission. The user-copy exception excludes automated/programmatic collection and database creation. These provisions need explicit assessment against preview edits and server-side creation of Parts; do not assume the confirmation button resolves the issue or that a second model call evades it. Google's pricing page distinguishes product-improvement use in free versus paid tiers. This memo identifies a documented constraint, not a legal determination. [Grounding terms](https://ai.google.dev/gemini-api/terms), [tier data-use table](https://ai.google.dev/gemini-api/docs/pricing).

Search availability does not establish downstream rights to republish arbitrary source material. Preserve source identity and retrieve only the contents evidence needed for the feature. Public accessibility also varies independently of whether a provider can cite a cached search result; citations alone do not establish that all chapter headings were read.

## What the acceptance corpus must prove

Before making an implementation-ready provider recommendation, run the same manually verified corpus through the proposed bounded workflow and the simpler baseline. Record model/version, query input, source URLs, matched edition, observed headings, evidence availability, result status, calls, tokens, elapsed time, and failures. Include repeated runs because one successful retrieval does not establish consistency.

- **Identity:** two editions of the same title, same-title different authors, translation and format differences. Distinguish a plausible work match from a supported edition match.
- **Structure:** numbered-only fiction, nested TOCs, chapter headings without numbers, front/back matter, duplicate headings, punctuation, and Unicode. Match the agreed flattening rule exactly, including order.
- **Coverage:** complete TOC, truncated TOC, sample chapter only, failed fetch, no credible source, and contradictory sources. Measure correct abstention and false claims of completeness separately from successful extraction.
- **Evidence:** every suggested entry is traceable to retrieved source text; remove or flag unsupported entries. Inject an unrelated instruction into a fixture page to verify it cannot direct the acquisition workflow or alter application behavior.
- **Usability and operations:** exact-match chapter precision, complete-list recovery, edition errors, User correction burden, p50/p95 elapsed time, and total attempt cost. An API timeout must remain distinguishable from “no chapters found.”

Suggested release gates, for the decision ticket to adopt or revise: zero invented headings and zero silent edition substitutions in the acceptance corpus; a defined coverage target, deadline, spend cap, and retry limit set before judging the provider. No numerical success rate is claimed here.

The findings sharpen the next decisions: minimum identity/evidence needed for a preview; treatment of incomplete lists and source typos; provider choice under citation/storage rules; and the measurable operating budget. They do not settle the User's partial-result preference or replace the architecture ticket.
